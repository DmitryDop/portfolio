# Шаблон кейсов портфолио

> Версия 1.0. Общий стандарт всех кейсов портфолио, не жёсткий макет. Применяется к существующим и будущим кейсам.

## 1. Назначение

Документ связывает редактуру в ChatGPT, макетирование в Figma и реализацию через Codex/Claude. Для отдельного кейса `docs/portfolio/cases/<slug>/content.md` отвечает за утверждённый текст и структуру, `design-brief.md` — за визуальное задание, а `handoff.md` — за передачу в разработку. Корневой `AGENTS.md` и production-протокол имеют приоритет во всех вопросах Git, deploy и rollback.

Утверждённые заголовки, тексты, теги, количество элементов, порядок секций и ссылки менять нельзя. Локальные композиционные решения агент принимает самостоятельно, если они не затрагивают контент и обратимы. Неподтверждённые факты, изменение смысла и действия с production требуют согласования.

## 2. Существующие паттерны

Перед макетированием изучить актуальные кейсы:

- `cases/design-system.html` — показатели, информационные карточки, визуальные секции;
- `cases/corporate-portal.html` — контекст, выполненные работы, продуктовые решения;
- `cases/reactor.html` — сценарии и акцентный блок;
- `cases/personal-cabinet.html` — состояния, сценарии, интеграции;
- `cases/nash-dom-pro.html` — исследование, UI Kit, честный итог;
- `cases/vacations.html` — цепочка сценариев, результат;
- `cases/palkahelp.html` — история проекта, цитата, запуск, ссылка.

Повторяются структуры `case-hero`, `case-section`, `case-media`, `media-card`; также есть специальные `case-band`, `case-quote`, карточки и показатели. Это библиотека **паттернов**, а не обязательная дизайн-система. Не создавать токены и новые библиотеки компонентов без отдельной задачи.

## 3. Структура кейса

Обязательны по смыслу:

1. **Карточка на главной** (если кейс добавляется в список): обложка, номер, заголовок, краткое описание, утверждённые теги и рабочая ссылка.
2. **Hero страницы кейса**: название, лид, теги и главное медиа, если оно предусмотрено; навигация в рамках существующего интерфейса.
3. **Содержательные секции**: только утверждённое количество и порядок.
4. **Итог / статус**: реальные результаты или честное состояние проекта; CTA только при известном URL.

«Контекст», «Что сделано», сетка карточек, цитата, показатели, финальный кадр — **не обязательные** блоки. Количество секций не фиксировано. Ничего не добавлять «для полноты».

### Типы блоков

- `text-media` — текст + крупный визуал;
- `text-only` — текст без медиа;
- `feature-grid` — строго заданное число информационных карточек;
- `stats` — проверенные цифры и факты;
- `quote` — авторская цитата;
- `process` — этапы или хронология;
- `gallery` — несколько экранов, состояний или деталей;
- `comparison` — «было / стало», только на реальных материалах;
- `video` — демонстрация движения;
- `custom` — новая композиция под задачу.

Нестандартный блок — **не ошибка**. Агент сопоставляет его с уже существующими кейсами и проектирует сильное решение в общей стилистике. Не создаёт новый компонент ради одноразового фрейма; сообщает, что придумал новый паттерн.

## 4. Формат блока в `content.md`

Для каждого блока задаются поля:

| Поле | Значение |
|---|---|
| `id` | Стабильный идентификатор, например `03-work` |
| `type` | Тип из списка или `custom` |
| `status` | `draft` / `content-approved` |
| `eyebrow` | Надзаголовок, если нужен |
| `title`, `subtitle` | Точные утверждённые строки |
| `body` | Точный текст или `none` |
| `items` | Карточки/пункты с фиксированным количеством и точными текстами |
| `tags` | Точный список тегов, если предусмотрены |
| `media` | Тип, состояние, роль и пропорции медиа |
| `cta` | Подпись, URL и действие (если есть) |
| `notes` | Исключения, запреты, интерактивность |

Отсутствующие поля не требуется выдумывать. Незаполненный фактический материал помечать `[УТОЧНИТЬ]` в `draft`; до `content-approved` такие вопросы должны быть разрешены.

Пример блока **без картинок**:

```yaml
id: 03-work
type: feature-grid
status: content-approved
title: От идеи до продакшена
subtitle: "<утверждённый текст>"
items:
  count: 4
  entries:
    - title: Концепция и арт-дирекшн
      body: "<утверждённый текст карточки 1>"
    - title: UX/UI и композиция
      body: "<утверждённый текст карточки 2>"
    - title: AI-production
      body: "<утверждённый текст карточки 3>"
    - title: Разработка и запуск
      body: "<утверждённый текст карточки 4>"
media:
  state: none
```

## 5. Состояния медиа

- **`placeholder`** — медиа предусмотрено, ассета ещё нет. В Figma сделать нейтральную подписанную заглушку: назначение, желаемое соотношение сторон (например, `DIAMOND / Hero / 16:9`). Не генерировать изображение без задания.
- **`ready`** — утверждённый ассет есть. Использовать его, не заменяя и не меняя смысл самостоятельно.
- **`none`** — медиа не предусмотрено. Не добавлять ни заглушку, ни иконку, ни декор ради заполнения пространства.

Видео дополнительно имеет источник, poster, поведение, состояние готовности. Пока ролика нет — подписанный placeholder, не имитация видео.

## 6. Макетирование в Figma

1. Изучить реальные кейсы: композицию, сетки, типографику, карточки, ритм, а не придумывать дизайн-систему с нуля.
2. Создавать **нативные редактируемые фреймы и текст**; Auto Layout — когда уместен. Плоский скриншот или HTML-превью не считаются готовым макетом.
3. Соблюдать точный контент и типы/количества элементов из `content.md`.
4. При новом блоке найти визуально убедительное решение; не запрашивать подтверждение на каждую мелочь, но сообщить о существенных дизайнерских решениях.
5. Сначала утверждать desktop-версию. По сложившемуся процессу Claude/Codex может делать адаптив от неё; обязательна последующая проверка реального мобильного отображения. Мобильные Figma-фреймы не являются обязательными для каждого кейса.
6. Taste Skill и другие UX/UI-подсказки — вспомогательные источники качества, а не право менять контент.

## 7. Текст и факты

Писать конкретно, живо, в авторской интонации, без нейрослопа, пафоса и пустых общих фраз. Не приписывать себе несуществующие исследования, конверсии, метрики, отзывы и бизнес-результаты. Различать концепт, учебный/pet project и коммерческую работу. Humanizer анализирует только временную копию `draft` в разрешённом расположении; исходник не передавать ему как цель записи. Предложения показывать в виде unified diff относительно неизменённого исходника. Только агент-редактор может внести в исходник явно утверждённые пользователем изменения; Humanizer не записывает их в исходник. После `content-approved` Humanizer не применять; для новой редакции сначала согласовать возврат в `draft`. Это правило одинаково для Codex и Claude Code и имеет приоритет над стандартным файловым режимом Humanizer. Если текст не помещается — сначала искать визуальное решение, а не тайком сокращать.

Детальные правила позже выносятся в `editorial-guide.md`.

## 8. Стадии

`draft` → `content-approved` → `design-review` → `design-approved` → `ready-for-deploy` → `published`.

- `content-approved`: зафиксированы тексты, порядок блоков, количество карточек, медиа и CTA.
- `design-review`: Figma-агент собрал редактируемый макет; перечислил новые паттерны, заглушки и вопросы.
- `design-approved`: арт-дирекшн завершён; ссылки на Figma-фреймы, ассеты, интерактивность и кнопки записаны в `handoff.md`.
- `ready-for-deploy`: вёрстка проверена на desktop и mobile, ссылки работают, визуал сопоставлен с Figma, существующие кейсы и сценарии не сломаны.
- `published`: публикация отдельно разрешена и проверена по production-протоколу.

Созданный макет **не даёт** разрешения на реализацию или деплой автоматически.

## 9. Проверка результата

- Есть все утверждённые блоки в правильном порядке, без самодеятельных добавлений.
- Заголовки, абзацы, теги, числа карточек и CTA точно соответствуют `content.md`.
- У каждого медиа указано `none`, `placeholder` либо `ready`.
- Новые решения оформлены аккуратно, макет нативно редактируется в Figma.
- В верстке соблюдены адаптивность, доступность основных действий и корректность переходов.
- **«Было → стало»: каждый ранее работающий сценарий продолжает работать.**
- Нет неподтверждённых фактов и выдуманных метрик.
- Нет автоматического deploy; действующие `AGENTS.md` и production-протокол соблюдены.
