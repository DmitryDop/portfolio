# Архитектурное ревью production deploy и reconciliation

Дата: 2026-10-29. Проект: личное портфолио Dopler.
Проверенная версия кода: `88b395c9c76bf818752514caf35a66acefc2d34f`.
Режим аудита: только чтение локального кода, Git и production metadata.
Состояние сервера — по последней проверке 28 октября; в ходе этого аудита сервер не опрашивался.

## Рекомендация

Упростить подтверждение владельца и сохранить проверки содержимого, историю
и защиту записи. Для личного статического портфолио отдельный подписант,
root-runner и новый контур ключей сейчас непропорциональны задаче.

Это рекомендация для новой согласованной версии протокола. Действующие требования
SSHSIG остаются обязательными, пока правила и код явно не изменены.

## 1. Причина рассинхронизации

В журнале последняя публикация — `00ad3f0f69984e4cfb118caec7e25afec37b1591`,
проверенная 19 октября в 16:17 по Москве. Затем появились изменения:

| Commit | Изменение |
| --- | --- |
| `e2409bd` | Девять изображений DIAMOND и CSS |
| `22c30a0` | Номер кейса DIAMOND |
| `acb5848` | Типографика девяти HTML-страниц |

Новых событий публикации после них в [журнале](../.deploy/history.json) нет.

`acb5848`, `59143e9` и `d25e672` имеют одинаковый production manifest.
Последняя серверная проверка 28 октября совпала с этим содержимым.
По hashes нельзя установить, какой именно из трёх commits использовали при загрузке.

Canonical manifest SHA-256 этих версий:

```text
8d247cf9ea4c083028fce0979ab7a3ce9ebeca2c93ba0550cdab68a70856a055
```

Подтверждённый разрыв: содержимое production обновилось, история публикаций
осталась прежней. Вероятная организационная причина — загрузка прошла без
завершения учёта metadata. Кто, когда и каким инструментом выполнил её,
по Git установить нельзя.

Архитектура способствует такому пропуску: текущий [CLI](../scripts/production.py)
предоставляет подготовку и проверки, но не единый цикл
«загрузить → проверить → записать результат».

## 2. Реальные риски

Для управляемого статического сайта основные риски — неправильная версия,
сломанные ресурсы, частичная загрузка и недостоверный rollback. Миграций БД
здесь нет; содержимое управляемых файлов восстанавливается из Git.

| Риск | Приоритет | Основная защита |
| --- | --- | --- |
| Обновление сайта без записи истории | Высокий: уже наблюдалось | Единый процесс публикации |
| Неверный SHA, каталог или набор файлов | Высокий | Pinned SHA, snapshot, allowlist, dry-run |
| Удаление чужих серверных файлов | Высокий | Запрет автоматического удаления |
| Частичная загрузка | Средний | Проверка результата, остановка без ложного успеха |
| Параллельные операции | Средний | Общий lock на полный цикл |
| Повреждение metadata при записи | Средний | Архив, журнал операции, восстановление |

Компрометация Mac или SSH-доступа имеет серьёзные последствия, но отдельная
подпись reconciliation защищает только согласие с планом. Она не закрывает
все пути изменения сайта или metadata — это признаёт и [текущая документация](production-reconciliation.md#ограничения).

## 3. Сравнение архитектур

| Механизм | Рекомендация |
| --- | --- |
| SHA-256 файлов по SSH и проверка HTTPS | Сохранить |
| Архив исходных metadata перед записью | Добавить как постоянный артефакт операции |
| Отдельное событие reconciliation | Сохранить; старую историю не переписывать |
| Неизвестный `previous` пустой | Сохранить обязательно |
| Подтверждение конкретного плана владельцем | Сохранить |
| Обязательная SSHSIG-подпись | Для принятой модели доверия можно заменить процедурным подтверждением |
| Root trust store, отдельная учётная запись, независимый runtime | Отложить |
| Повторная проверка перед записью | Сохранить |
| Lock и восстановление прерванной записи | Сохранить |

Пяти пунктов упрощённой схемы недостаточно без защиты записи. Архив позволяет
восстановить metadata, но сам по себе не предотвращает гонку или рассогласование
трёх файлов. Атомарная замена отдельного файла также не создаёт транзакцию
для всех трёх. См. [документацию `os.replace`](https://docs.python.org/3/library/os.html#os.replace).

## 4. Минимальный безопасный процесс

1. Подготовить план: SHA, manifest hash, сервер, recorded current/previous,
   ожидаемые изменения metadata.
2. Проверить фактические SSH/HTTPS hashes, показать расхождения владельцу.
3. Получить отдельное явное подтверждение точного hash плана.
4. Взять общий lock и повторно проверить сервер, план и исходные bytes metadata.
5. Сохранить проверяемый архив исходных metadata и результатов проверки.
6. Добавить событие reconciliation через существующий механизм безопасной записи.
7. Перечитать историю и зеркала. При ошибке остановиться, загрузку не повторять.

Подтверждение в этой модели — запись согласия владельца в рабочем процессе.
Оно не обеспечивает криптографическую независимость от агента с полным доступом
к той же учётной записи. Для личного проекта это допустимый компромисс,
если агент рассматривается как контролируемый инструмент.

Отдельно нужен единый исполнитель deploy, чтобы успешная загрузка не оставалась
без учёта. Ошибка записи после загрузки должна переводить операцию в состояние
«требуется восстановление metadata», сохраняя доказательства.

## 5. Минимальные изменения и тесты

Изменения:

- Согласовать новую модель подтверждения в протоколе и skills. Не добавлять
  `--skip-signature` и не подменять существующий guard.
- Переиспользовать сборщик доказательств, неизменяемые события
  и [журнал прерванной записи](../scripts/reconciliation.py).
- Добавить постоянный архив metadata и подтверждения.
- Объединить стадии публикации общим исполнителем и lock. Сейчас lock обычной
  записи берётся уже на этапе сохранения metadata в [`_persist_history`](../scripts/production.py).
- Сохранить прежние правила deploy, rollback, exclusions и запрет выдуманного `previous`.

Обязательные тесты:

- Несовпадение hashes или ресурсов блокирует операцию.
- Изменение плана, сервера или metadata отменяет подтверждение.
- Старые события неизменны, reconciliation оставляет неизвестный `previous` пустым.
- Ошибка архивирования не меняет metadata.
- Параллельная и повторная операции блокируются.
- Прерывание на каждой стадии записи восстанавливается без повторного upload.
- Последующие deploy/rollback сохраняют корректные переходы.

## 6. Итоговая оценка рисков

Принять упрощённую модель для одного владельца и одного процесса публикации.
Сосредоточить изменения на учёте завершённых операций, проверках содержимого
и восстановлении после сбоя.

Остаточный риск — сторонние ручные загрузки, кратковременное частичное состояние
сайта и компрометация рабочей машины. Предложенная схема уменьшает эксплуатационные
ошибки, сохраняя понятный предел защиты. Независимый криптографический контур
оправдан при появлении нескольких операторов или требования защищаться
от злонамеренного агента.

изменение metadata или production-операции.
