# Сверка непустой production-истории

`reconciliation` — отдельное наблюдение фактического production, когда файлы
соответствуют известному Git manifest, но отличаются от записанного current.
Операция не выполняет загрузку, deploy, rollback или первоначальную baseline adoption.
Серверные файлы не изменяются. Реализация: `scripts/reconciliation.py`.

## Состояние и неизменяемость истории

- Требуется непустая валидная история и согласованные зеркала. Повреждённая либо
  legacy metadata без evidence блокирует подготовку плана.
- Добавляется ровно одно событие `operation=reconciliation`, `kind=observation`.
  `rsync_exit` запрещён. Старые события, hashes и evidence остаются неизменными.
- `before` хранит ранее записанный current, но не утверждает, что эта версия
  наблюдалась непосредственно перед сверкой. В подписанном плане сохраняется
  также `recorded_previous`. `before_evidence` старого current не подделывается.
- Новый current — наблюдаемый commit. Новый previous всегда пустой: порядок
  неучтённых публикаций неизвестен. Старые подтверждённые версии остаются в истории.
- Совпадение с Git manifest доказывает содержимое, а не дату, способ загрузки
  или единственность исторического commit: несколько commits могут иметь один manifest.
- Повторная сверка уже записанного содержимого запрещена. UUID операции уникален
  для всей истории, receipt ID владельца нельзя использовать повторно.
- После reconciliation deploy/rollback требуют отдельного `live_current` observation.
  После успешного deploy B состояние будет B/A, где A — сверенный current.

## Подготовка плана — только чтение

```sh
PYTHONDONTWRITEBYTECODE=1 python3 scripts/production.py reconciliation-plan \
  d25e6727b111f9f8bfeb89c9415e3cca8ecef958 \
  --reason 'Неучтённые публикации; непосредственная предыдущая версия неизвестна'
```

Команда читает Git и metadata, выводит JSON; не создаёт файлов, не обращается
к сети и не выполняет reconciliation. `check_plan` повторно сверяет:

- полный SHA, manifest и его canonical SHA-256, наличие ресурсов;
- remote path, HTTPS URL и абсолютный путь checkout;
- SHA-256 исходных bytes всех трёх metadata-файлов, current, previous и history tip;
- уникальный UUID операции, причину и политику `previous=''`.

Hash плана — SHA-256 canonical JSON без поля `hash`, а не подпись.
Изменение любого поля требует нового подтверждения.

## Доверенное подтверждение владельца

Реализована проверка SSHSIG через системный `/usr/bin/ssh-keygen -Y verify`.
Публичный trust store фиксирован: `/etc/portfolio-production/allowed_signers`.
Его файл и все разрешённые абсолютные родительские каталоги должны принадлежать
root и не допускать запись группе/остальным. Используется identity `portfolio-owner`.
Путь не переопределяется аргументом, переменной окружения или файлом проекта.
Без trust store операция закрыта с `PermissionError` до наблюдения и записи metadata.

Trust store должен установить независимый системный администратор по отдельному
разрешению. Ключ владельца и подписывающее приложение должны находиться вне среды
агента. Репозиторий не создаёт production-ключей, не регистрирует доверие и не содержит
команды, которая сама выдаёт себе approval. Старый baseline guard не изменён.

Владелец проверяет полный план и подписывает canonical JSON следующих claims:

```json
{
  "purpose": "reconciliation",
  "plan_hash": "SHA-256 полного плана",
  "operation_id": "UUID из плана",
  "receipt_id": "новый UUID подтверждения",
  "issued_at": "timestamp с часовым поясом",
  "expires_at": "timestamp с часовым поясом"
}
```

Namespace подписи: `portfolio-production-reconciliation`.
Receipt имеет вид `{"claims": {...}, "signature": "-----BEGIN SSH SIGNATURE-----..."}`.
Срок действия не более 10 минут; подпись, срок и доверенный ключ проверяются перед
блокировкой и ещё раз после нового наблюдения. Простое «да», `DEPLOY`, локальный
флаг, callback с True или самостоятельно созданная агентом подпись не подходят.

Публичный API записи: `save_reconciliation(repo, plan, receipt)`. CLI записи намеренно
нет. API самостоятельно вызывает встроенный сборщик; callback проверки или approval
пользовательскому вызову не передаётся. `save_history`, старый `_persist_history`
и `transition(operation='reconciliation')` этот путь не заменяют и отклоняют его.

## Доказательства и гонки

Под общей эксклюзивной `.deploy/metadata.lock` выполняется новое наблюдение:

1. SSH с `BatchMode=yes` и `StrictHostKeyChecking=yes`; SHA-256 каждого managed-файла.
   Managed symlinks, включая symlink-каталоги внутри root, запрещены. Дополнительные
   серверные paths перечисляются; `.htaccess` и `.well-known/` хешируются.
2. HTTPS каждого manifest URL и главной `/`: проверка TLS, status 200 и SHA-256 тела.
   Перенаправления запрещены. Запрашивается `Accept-Encoding: identity`; неожиданный
   compression блокирует операцию. Чтение ограничено размером Git blob плюс один байт.
3. Повторная SSH-проверка. Изменение hashes, inventory либо защищённых файлов
   между двумя SSH-наблюдениями блокирует запись.

Evidence сохраняет фактические stdout/stderr SSH, exit codes, URL/status/hashes,
inventory, время начала/конца и свежий challenge. Старое наблюдение не принимается:
challenge создаётся под lock, timestamps должны попадать в текущий интервал.
Исходные bytes metadata повторно проверяются после сбора доказательств.

Lock совместим с существующими операциями, работающими через production helper.
Несогласованные изменения в обход lock не поддерживаются. Между последним чтением
сервера и записью локального журнала остаётся короткое окно: на период применения
нужно организационно исключить сторонние загрузки. Локальный lock не блокирует сервер.

## Безопасная запись и прерванная операция

До первой замены metadata записывается durable write-ahead journal
`.deploy/reconciliation-pending.json`: исходные и целевые bytes трёх файлов,
operation ID и canonical hash. Каждая запись использует временный файл,
flush, fsync, atomic replace и fsync каталога. Порядок: WAL → history → current → previous.
History — точка commit. WAL удаляется только после проверки результата.

Пока WAL существует, `inspect`, baseline, deploy и новая reconciliation блокируются.
Нельзя повторять reconciliation, сбрасывать history либо вручную исправлять SHA.
Read-only диагностика восстановления:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 scripts/production.py reconciliation-recovery-plan
```

План привязывается к точным bytes WAL и фактических metadata, ID события, manifest
и результирующим current/previous. Возможны только два действия:

| Наблюдаемое локальное состояние | Разрешённое действие |
| --- | --- |
| Все metadata ещё исходные; history не заменена | `abort-uncommitted`: убрать WAL, metadata оставить исходными |
| History уже целевая; зеркала имеют исходные/целевые bytes | `finish-mirrors`: завершить только зеркала, history не перезаписывать |
| Иное содержимое либо нарушенная история/WAL | Отказ; отдельное расследование |

Публичный API `recover_reconciliation(repo, plan, receipt)` требует нового receipt,
purpose `reconciliation-recovery`, namespace `portfolio-production-reconciliation-recovery`.
Также повторно проверяется исходная подпись владельца сохранённого reconciliation-события;
её истёкший срок не превращается в новое разрешение. Нужный исторический публичный
ключ должен оставаться доступным в доверенном хранилище.

Восстановление не обращается к серверу, не создаёт нового события и не повторяет
reconciliation. Оно завершает ранее проверенную транзакцию. После него для дальнейших
операций обязательна обычная свежая проверка production. Подписанные recovery-план
и receipt вызывающая сторона сохраняет в отдельном аудите; они не вписываются
задним числом в неизменяемое событие.

При повторном прерывании строится новый recovery-план по текущим bytes.
Оставшийся после SIGKILL stale `metadata.lock` не удаляется автоматически:
сначала проверка отсутствия активного процесса, затем отдельное разрешение владельца.
Ошибку fsync нельзя объявлять успехом. Если WAL уже отсутствует, но событие
зафиксировано, нужно проверить историю; повторная reconciliation запрещена как no-op.

## Границы доверия

- SSHSIG подтверждает согласие владельца с планом. Она не подписывает будущие ответы
  сервера. Доказательства собирает проверенный код в доверенной среде исполнения.
- Hash chain и WAL hash обнаруживают повреждения, но не заменяют подпись/внешний аудит.
  Историческая `validate_history` проверяет структуру и связь claims с планом,
  а не выдаёт новое approval по истёкшему receipt.
- Агент с произвольной записью Python-кода или metadata технически способен обойти
  библиотеку. Для production запуска нужен проверенный runner вне изменяемого checkout
  и независимый подписант. Внутренние функции запрещено вызывать для обхода guards.
- HTTPS/SSH интеграция проверена локальными имитациями транспорта; эти тесты
  не доказывают доступность, актуальные host keys или TLS production.
- Сбой/нечестное поведение диска и не соблюдающие lock внешние процессы требуют
  отдельного расследования. Автоматического ремонта произвольного повреждения нет.

## План применения для текущего портфолио — не выполнен

1. Отдельно согласовать код и его commit/push; зафиксировать версию доверенного runner.
   Отдельно установить owner trust store, не передавая агенту закрытый ключ.
2. Сохранить исходные metadata и историю неизменным архивом. Исключить параллельные
   публикации. Подготовить план для `d25e6727b111f9f8bfeb89c9415e3cca8ecef958`.
3. Проверить canonical manifest SHA-256:
   `8d247cf9ea4c083028fce0979ab7a3ce9ebeca2c93ba0550cdab68a70856a055`.
   Утвердить полный план и получить owner-signed receipt через независимый канал.
4. Только после отдельного разрешения вызвать публичный API в доверенной среде.
   Он повторит SSH/HTTPS наблюдение и запишет `current=d25e672…`, `previous=''`.
   Исторический `d9bfc32…` остаётся в журнале, но не назначается предыдущим.
5. Проверить согласованность истории, event ID, receipt, отсутствие WAL и lock,
   неизменность серверных файлов. Commit/push metadata согласовать отдельно.
6. Подготовка deploy карточки `540dd63…` — отдельная задача с отдельной командой `DEPLOY`.

В ходе локальной реализации реальная reconciliation, recovery и owner provisioning
не выполнялись. Файлы сайта и production metadata не изменялись.
